## 2. 初次核对的衔接问题与处理状态

### 2.1 首个管理员不能依赖注册邀请码

“邀请注册 → 管理员生成邀请 → 注册后再提升管理员”存在首次启动循环。5.2 已提供独立的本地/远程 bootstrap 脚本：离线读取邮箱和密码、生成与 Worker 相同格式的哈希、创建首个管理员；数据库已有管理员时默认拒绝重复引导。密码不写入 Git、不放在命令行参数或日志里。之后的用户才走管理员邀请码注册。

### 2.2 统一标的身份，之后再接多市场目录

5.4 已用 0004 将唯一约束改为市场 / 品种 / 代码组合。原 `US:SOXX` / `HK:2800` 等 ID 和 URL 保留，新标的使用 `CN:etf:510300` 这样的稳定 ID 与公共代码，目录、任务和持仓关联不再依赖裸代码。

### 2.3 入库结果必须有读出与展示链路

当前 `domains/model.ts` 在模块加载时直接解析 `ai-chips.json` 与 `ai-storage.json`；配料表、重仓影响和对照计算使用这些静态对象。`/api/catalog` 只返回基金元数据，不返回持仓或产业研究。

5.4 已交付详情、持仓与行情读取接口及动态详情页，按管理员维护的公司归属计算产业链分组；现有精品研究及全局 PK 保留静态核对资料，避免混合报告期。

### 2.4 保留数据口径与来源

初始表结构不足以重建现行契约。5.4 已通过快照表与共享 Schema 补齐：

- 行情保留指数/交易价格/净值类型、币种、单位、时区、上游来源 URL、获取时间、失败/陈旧状态与复权口径；用 `marketSnapshotSchema` 验证读出结果。
- 持仓保留披露截止日、来源 URL、完整/前十覆盖范围、披露数量等快照级信息；按快照原子发布，不能让用户读到半份新持仓。
- 自动采集持仓不能自动编造近期影响胶囊；缺乏研究证据的标的展示“待补充研究”。

### 2.5 用户持仓字段先对齐

前端存的是 `units` + `costMinor`（总成本的最小货币单位），D1 预留的是 `quantity` + `cost_price`（单价语义）。5.5 建议保留总成本的精确整数表示并显式迁移字段，避免除以份额产生舍入损失。导入时保持币种、总成本和份额原值；不能把 ETF 收盘价写成净值。

### 2.6 开发与部署入口（5.1 已对齐）

- `pnpm build` 保留静态目录模式；`pnpm build:worker` 使用 `.env.worker` 构建到独立的 `apps/web/dist-worker`，从 `/api/catalog` 读取 D1。网络/超时/服务/数据异常时只对公共目录回退到预缓存的 `catalog.json`，显示资料日期与重试入口；取消请求不触发回退，两端都不可用则显示可重试错误。
- `pnpm dev:web:worker` 的全部 `/api` 请求代理到 Worker 8787；原 `pnpm dev:market` 保留 8788 行情代理。5.4 已接入 `/api/market`，只展示 D1 已发布的真实口径日线，无数据时显示暂无数据。
- CI 已运行 `pnpm check:worker`：构建、Worker dry-run、全新临时 D1 迁移/两次种子导入、实际 Wrangler API 与深链验证。这些检查不部署到 Cloudflare。Cloudflare 预览 workflow 已在仓库停用，并增加 `SORA_CLOUDFLARE_PREVIEW_ENABLED=true` 的显式启用条件；云端采集已移除定时触发并默认关闭，见 [采集说明](./INGEST.md)。正式远程部署在 5.6 另行配置。

该命令重新构建 Worker 前端并启动本地 Worker。需要 React 热更新时，保持 Worker 运行，另开终端执行 `pnpm dev:web:worker`，访问 Vite 输出的地址。

```bash
pnpm check

```

`check:worker` 的数据库在系统临时目录中创建，结束后清理；不会修改开发数据库或远程资源。它会验证新库迁移、种子幂等、目录与静态基线一致、ETag/HEAD、未知 API JSON 404、写操作 405、基金详情深链与回退静态文件。开发数据库保存在 `apps/worker/.wrangler`，不要与远程 D1 混用。D1 的本地与远程环境默认隔离，见 [Cloudflare 本地开发文档](https://developers.cloudflare.com/d1/best-practices/local-development/)。

## 5. 5.2 鉴权使用与边界

本地配置（首次创建，已有 `.dev.vars` 时自行合并，不覆盖原值）：

```bash
cp apps/worker/.dev.vars.example apps/worker/.dev.vars
pnpm build:worker
pnpm db:setup:local
pnpm --filter @sora/worker admin:bootstrap --local
pnpm --filter @sora/worker dev
```

初始化脚本交互读取邮箱和不回显的密码（12～128 字符）；也可从标准输入接收 JSON，避免把密码写入命令行或历史。它直接创建首个管理员；已有任意管理员或相同邮箱时拒绝执行，不提升/覆盖已有用户。不要把真实密码写进仓库文件。远程引导须明确改为 `--remote`，在 5.6 部署时执行。

在 `/login` 登录后进入“我的账号”，管理员可生成七天有效、单次使用的邀请链接。原始邀请码仅在本次生成响应中出现，D1 只存哈希；普通用户服务端返回 403。新账号角色始终为 user。邀请创建同时写入审计记录；5.3 已提供完整 `/admin` 和用户禁用/重置密码界面。

接口：`GET /api/auth/config`（只返回公开 site key）、`GET /api/auth/me`、`POST /api/auth/register`、`POST /api/auth/login`、`POST /api/auth/logout`、`POST /api/admin/invites`。所有账号响应不缓存；写请求必须包含允许的 Origin 和 JSON Content-Type，正文最多 8 KiB。密码使用带独立 16 字节 salt 的 PBKDF2-SHA256（100,000 次），会话为 32 字节随机令牌，D1 只存 SHA-256；Cookie 使用 HttpOnly/Secure/SameSite=Lax 和 30 天有效期，每天最多滑动续期一次。已禁用用户不能使用现有会话；主动注销会删除服务端会话。

登录每 IP 每 15 分钟最多 60 次、每邮箱每 15 分钟最多 10 次；注册每 IP 每小时最多 10 次、每邮箱每 15 分钟最多 10 次；邀请码生成每管理员每天最多 30 次。429 响应带当前窗口剩余秒数的 Retry-After，过期记录分批清理。

`.dev.vars.example` 是 Cloudflare 官方测试 keys，仅允许在 localhost/127.0.0.1/IPv6 loopback 使用。正式环境缺少配置或使用测试 keys 时拒绝鉴权，不能通过未配置来跳过验证。正式 `TURNSTILE_SECRET_KEY` 用 Worker Secret 保存；公开 `TURNSTILE_SITE_KEY` 可用 Worker 变量，注册/登录页面从 config 接口读取，不需要把 Secret 注入 Vite。Siteverify 验证成功后还会检查生产 hostname/action。[官方测试 keys](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)

可选 Vite 热更新开发需设置 `AUTH_TRUSTED_ORIGIN` 为 Vite 的准确 origin；示例为 `http://127.0.0.1:5173`。若 Vite 换了端口或主机名，必须同步修改并重启 Worker。浏览器直接访问 Worker 时无需额外 Origin。

`pnpm check:worker` 的独立临时 D1 验收已覆盖引导（含重复拒绝）、真实 workerd PBKDF2 登录、并发邀请码注册、普通用户越权与注销失效。仅测试入口 `src/test/runtime.ts` 模拟外部 Siteverify，正式配置始终部署 `src/index.ts`，不会包含该替身。

5.5 已实现登录后的基金关注与持仓保存到账号；原本地记录仅在用户选择导入后上传，方向关注和研究复盘仍留在本地。详见 [个人数据说明](./PERSONAL.md)。

## 7. 5.3 管理后台使用与边界

已有本地库先执行 `pnpm db:setup:local`，应用 `0003_admin.sql` 后启动 Worker。管理员可从顶栏账号菜单或“我的账号”进入 `/admin`。匿名用户跳转登录并保留返回地址，普通用户看到 403 页面，所有管理 API 另行校验真实会话与当前管理员角色，不能靠改前端状态绕过。

后台有三个栏目：

- 用户管理：按邮箱或名称搜索、每页 20 条；启用/禁用、授予/取消管理员、重置密码均需在确认框核对目标账号。每次操作携带读取时的用户版本，409 时自动重读，避免覆盖别人刚做的修改。
- 邀请码管理：生成、按创建时间分页查看、撤销未使用且未过期的邀请。列表仅提供管理 ID、状态与创建/使用信息，不能还原原始邀请码；原始邀请链接仍仅在生成时显示。
- 审计日志：分页查看，并按操作类型筛选。成功的管理写入记录操作者、目标、时间和变更说明；不记录明文密码或密码哈希。

禁用、启用、角色变更和重置密码都会删除目标账号的全部会话；启用或授予管理员后需要重新登录。密码重置由服务端生成随机新密码，只在本次成功响应和结果界面显示，关闭后不再提供查询。管理员重置自己的密码或修改自己的角色/状态时，旧 Cookie 会被清除，页面保留本次操作结果并引导重新登录，避免来不及保存新密码。

数据库触发器禁止禁用、降级或删除最后一个 `role='admin' AND disabled_at IS NULL` 的账号，已禁用的管理员不计入保护数量。保护在数据库写事务内执行，因此两位管理员并发自降级或互相禁用仍至少保留一名可用管理员。请求内的实际写入还会再次检查操作者角色、禁用状态和当前会话是否有效。

用户更新、旧会话删除和审计使用同一 D1 batch：只要任一语句失败，整批回滚。邀请撤销与注册单次消费也由事务序列化，不能同时撤销成功又注册成功。除邀请码生成的每日限额外，其他管理写入每位管理员每 15 分钟最多 100 次。

新增/扩展 API（均 `Cache-Control: no-store`）：

| `PATCH /api/admin/users/:id`          | `{revision, action:'setDisabled', disabled}` / `{revision, action:'setRole', role}` / `{revision, action:'resetPassword'}`；返回新版本，密码重置额外返回本次新密码 |
